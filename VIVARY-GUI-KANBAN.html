How The System Works

Workspace lifecycle

1. CreateGUI calls /api/workspaces/scaffold.
2. ScaffoldBackend calls create_vivary.scaffold_workspace.
3. Doctorcreate-vivary validates required files and graph health.
4. RegisterRegistry stores a pointer, not a copy of workspace files.
5. IndexFTS5 indexes markdown, excluding identity and secret files.

Agent turn lifecycle

1. SessionManager creates sandbox and stores runtime plus tool mode.
2. EnvAgent gets Vivary Python toolchain and sandbox metadata.
3. RunCodex runs exec --json in the sandbox cwd.
4. ParseJSONL maps to typed AgentEvent records.
5. RenderFrontend reducer renders answer-first chat and receipts.

Approval lifecycle

  1. Policy classifies risk deterministically from command, tool kind, target, and protected paths.
  2. Reads can auto-allow in auto mode; writes, execute, network, and delete ask by default.
  3. Approval card lets Jeff choose allow once, allow always, reject once, or reject always with steering.
  4. Global policy persists at ~/.vivary-gui/policy.json. Project policy is future work.
  5. Real mid-run Codex approval is still gated on protocol proof from app-server, exec-server, remote-control, or MCP.

Tool creation lifecycle target

  1. Model proposes a project-local tool under .vivary/tools/<tool-id>/.
  2. Manifest declares id, title, entrypoint, args schema, risk, creator, version, and hash.
  3. Backend discovers and validates the manifest. Path traversal and global mutation are rejected.
  4. First run of a new or modified tool requires approval, with hash-bound trust.
  5. Execution happens inside the session sandbox and emits normal tool receipts.

Roadmap Guidelines

Engineering rules

  • Plan tests before edits. Each story has owned files, acceptance criteria, and verification evidence.
  • Default to backend contracts when frontend files are owned by another worktree.
  • Never hide capability behind optimistic UI. If the backend cannot prove it, the frontend must show it as gated.
  • Read-only is the default agent mode. Workspace-write is explicit and visible.
  • Missing tools are evidence to report, not a reason to install without approval.

Product rules

  • The GUI is the control layer. Vivary workspaces remain plain files on disk.
  • Use create-vivary for workspace shape. Do not create a second demo-only schema.
  • Every agent action should leave a receipt: command, risk, status, output, file change, or approval decision.
  • Keep answer-first chat. Receipts support trust; they do not bury the answer.
  • Human testing is a release gate, not a courtesy check after merge.

Tool-authoring rules

  • Tools live in .vivary/tools/<tool-id>/ and declare a manifest.
  • Tool source cannot escape its directory. Reject absolute paths and .. traversal.
  • No global installs, profile edits, PATH writes, or host-level mutation from generated tools.
  • Trust binds to tool hash plus scope. Editing a tool invalidates prior allow-always approval.
  • Generated tool execution uses the same sandbox env as agent turns.

Branch and collaboration rules

  • Current implementation worktree is vivary-GUI-obs-loop; original vivary-GUI remains coordination/reference.
  • Do not edit files dirty in the Meso worktree unless the owner coordinates first.
  • Checkpoint locally after verified slices. Do not push, PR, merge, publish, or consolidate without Jeff.
  • Record stale claims as bugs. Docs and roadmaps must match implemented behavior.
  • Stop at hard gates instead of batching them for later.
