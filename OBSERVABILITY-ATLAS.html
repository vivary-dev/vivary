The Vivary GUI, end to end

You're taking over the observability + chat surface of the Vivary GUI — a local web app that drives agent-native workspaces. This atlas is your map: every module, every surface that connects to the next, and exactly where today's design ends and the redesign begins. It's built from a first-principles read of the live code on this branch, ground-truthed against the tools installed on this machine.

The one sentence to anchor on
A chat turn is a stream of typed events that flows: agent CLI → a Runtime parser → AgentEvent → the Manager's per-session queue → a WebSocket → a React reducer → rendered blocks. Everything in this redesign is about making those events richer (at the parser) and rendering them structured (at the reducer). Get that spine, and the rest is detail.
What it is
A local cockpit. FastAPI backend on 127.0.0.1:8765, React/Vite SPA on :5173. Persistent chat in the center, contextual workspace views on the right.
What's underneath
Vivary's engines. tropo (graph), ozone (review), exo (orchestration) — the published PyPI CLIs, reached as subprocesses. The GUI never reimplements them.
What we're fixing
The wall of text. Codex turns render as ~2,000 lines of undifferentiated output before the answer. We make them collapsible pills, a reasoning box, a privileged answer — and add real approvals.

The 30-second mental model

Four layers. Data flows down on a request, events flow up on a turn. Each layer only knows the one below it through a narrow contract — that's why the redesign is tractable.

① Frontendapp/frontend — React + Vite + TS. The 3-column shell, the chat reducer, the workspace views. Talks to the backend over REST + one WebSocket per session.
② Backendapp/backend/vivary_gui — FastAPI. Routers (HTTP/WS) → Services (the agent Manager, gates, sandbox, search index). Owns session lifecycle and the event stream.
③ Runtimesservices/agents — one adapter per agent CLI (codex, claude, echo). Each turns a raw CLI line into typed AgentEvents. This is where Phase A lives.
④ Vivary enginesbridge/ — the seam to the published tropo/ozone/exo CLIs (run via python -m) plus create-vivary for workspace doctor. Read-only views.
Why this separation matters for you
The redesign touches layers ① and ③ almost exclusively. The Codex parser (③) starts emitting rich events; the chat reducer + components (①) start rendering them. Layer ② mostly passes events through unchanged (it already does), and layer ④ isn't touched at all. Small blast radius by design.

The same path, in code

Read these four snippets top-to-bottom and you've read the spine of the app.

# ② backend — agents/base.py · the contract every runtime implements
class Runtime:
    name: str; label: str
    multi_turn: bool = False        # can it --resume a prior conversation?
    stderr_is_error: bool = True     # Codex flips this False — it writes its transcript to stderr
    def build_command(self, prompt, resume=None) -> list[str]: ...
    def parse(self, line: str) -> list[AgentEvent]: ...   # ← the redesign's center of gravity

class AgentEvent:                       # the universal currency on the wire
    type: str; text: str = ""; tool: str = ""; meta: dict = {}
# ② backend — manager.py · spawn, read both streams, parse→emit, then diff gates
async def _run_turn(self, sess, rt, proc):
    async def read(stream, is_stderr):
        async for raw in stream:
            line = raw.decode(...).rstrip()
            if is_stderr and rt.stderr_is_error: self._emit(sess, AgentEvent("error", line))
            else:
                for ev in rt.parse(line): self._emit(sess, ev)   # ← hop 02→03
    await asyncio.gather(read(proc.stdout, False), read(proc.stderr, True))
    # …on exit: any NEW gates/*.md that appeared this turn → emit "gates_open" + pause
# ① frontend — api/client.ts · token rides the WS subprotocol, never the URL
export const openSessionWs = (id) => new WebSocket(sessionWsUrl(id), ['vivary', `token.${TOKEN}`])
# ① frontend — ChatPanel.tsx · the reducer (hop 05) and the live wiring
ws.onmessage = (m) => {
    const ev = JSON.parse(m.data)
    setItems((p) => apply(p, ev))                          # fold event into the transcript
    if (ev.type === 'result') setObs(... += tokens, cost)   # update the header meter
    else if (ev.type === 'gates_open') { loadGates(id); setAwaiting(true) }  # pause for approval
}

The three runtimes — and why Codex is the problem child

All three implement the same Runtime contract; they differ only in how rich their parse() is. This table is the diagnosis.

Today — the culprit, verbatim
class CodexRuntime(Runtime):
    multi_turn = False
    stderr_is_error = False  # transcript goes to stderr
    def build_command(self, prompt, resume=None):
        return [exe, "exec", "--", prompt]
    def parse(self, line):
        return [AgentEvent("text", line)] if line.strip() else []

Every line — commands, output, reasoning, metadata — becomes an undifferentiated text block. The UI can't tell a command from an answer.

Target — structured at the source
def build_command(self, prompt, resume=None):
        cmd = [exe, "exec", "--json",
               "--skip-git-repo-check", "-C", cwd,
               "--sandbox", mode]          # read-only by default
        if resume: cmd += ["resume", thread_id]
        return cmd + ["--", prompt]
    def parse(self, line):
        ev = json.loads(line)                # JSONL, one event/line
        # map item.type → reasoning | tool | file_change | …

Each line is now a typed item. The parser maps it to the rich events; the UI renders pills, a reasoning box, diffs.

Subtle gotcha you'll hit
Codex writes its human transcript to stderr, which is why stderr_is_error=False today. Once you move to --json, the structured events come on stdout. You'll likely keep stderr non-fatal (it may carry warnings) but stop treating it as the content channel. Confirm against a captured fixture before assuming.

The new chat components (Phase A, frontend)

Today ChatPanel.tsx has one <Block> that renders user|text|tool|status|error, with the tool card always expanded. The redesign replaces it with a small set of composable, collapsed-by-default components — all styled from the existing theme.ts tokens, so no design system work.

ToolPill
One line: ◐ Read · README.md · ✓ — kind icon + verb + target + status + diffstat. Collapsed by default; click → command + aggregated_output + exit/duration. Color = risk (mint read · amber write · red execute/delete).
ReasoningBox
One live line that updates while thinking, then collapses to "Thought for N s". Pinnable open. Shows the summarized trace, never raw. Two hard rules: don't auto-collapse while being read; don't expand-by-default and bury the answer.
FileChange
Per-file diff list from file_change.changes[]. Route edits here, not into the inline text stream (the single biggest clarity win other harnesses found). Stretch: per-hunk accept/reject before the write.
PlanRail
todo_list items as a live checklist — the agent's plan, ticking off in place. Plus a density control (Compact/Balanced/Detailed) and repeat-consolidation ("Read ×3").
The hierarchy rule
The agent_message (final answer) is the only full-fidelity element — rendered with the existing <Markdown> serif treatment. Everything else is a collapsed receipt or a side panel. Color is spent only on the live/active step. That's the whole anti-wall-of-text thesis in one line.

The approval system — the centerpiece & the differentiator

This is what makes the GUI more than a transcript viewer. Two halves: a deterministic policy engine (backend) that decides auto/ask/deny per action, and an ApprovalCard (frontend) with real buttons.

Risk tiers — classified deterministically, never self-labeled by the model

read → auto write → ask execute / delete → always ask network → ask protected path → never auto
The three-rung ladder (default the middle)
Manualask for everything
Auto ◀ defaultread auto · write+execute ask
YOLOallowlist drives; minimal asks
Real buttons — deny doubles as steering
▲runrm -rf build/execute
Allow once Allow always ▾ (command·project·global) Deny + "do X instead"

Mirrors Codex's CLI prompt & ACP's allow_once / allow_always / reject_once / reject_always.

The rules that make it not annoying

  • Allowlist-first, never denylist-first. Denylists are bypassable (Base64, subshells). Match by longest-prefix / word-boundary; deny beats allow.
  • "Always" = a pattern-scoped, persisted rule, not an exact string. Codex's #1 documented pain is re-prompting on slight variation — we fix it by extracting a safe prefix and persisting it (command / project / global scope).
  • Protected paths never auto-approve: .git, .env, config, dotfiles.
  • Circuit-breaker: cap auto-approvals per turn/session, then fall back to ask. Stops a runaway loop.
  • Persistence: ~/.vivary-gui/policy.json (global) + per-workspace .vivary/rules (project, version-controllable).
Keystone unknown #1 — the live-interception protocol (resolve before Phase B)
codex exec is one-shot and non-interactive — I confirmed on this machine that --ask-for-approval is a global flag and, under exec, only on-failure/never make sense (there's no TTY to answer a prompt). So observability ships on exec --json, but live mid-run approval needs a bidirectional surface: codex app-server (experimental JSON-RPC, what the IDE uses), codex mcp-server (stdio MCP), or the newer exec-server/remote-control (both present in 0.139.0). Spike these first; the choice sets the backend shape for the approval half. Target ACP vocabulary.

Gates — the approval mechanism that already works

Before the live approval system exists, there's already a turn-boundary gate: a Vivary-native human checkpoint. Understanding it matters because (a) it ships today and (b) the redesign keeps it as a differentiator (Codex cloud has no mid-run gate).

1
snapshot
send() records which gates/*.md are open before the turn.
→
2
agent raises
Mid-work, the agent writes a new gates/<id>.md with status: open and stops.
→
3
diff → pause
On exit, _run_turn diffs open gates. New ones → gates_open event, status awaiting.
→
4
you decide
Inline card: Approve / Reject. Writes frontmatter status (working-tree only — never a commit).
→
5
resume
All gates decided → resume() re-prompts the agent with the decision note (via --resume).
A gate is just a file
---
status: open          # → approved | rejected
gate: push to origin/main
command_intent: git push
---

services/gates.py reads/writes this frontmatter. No database — the file is the source of truth, consistent with Vivary's whole philosophy.

Why session-scoped

The agent runs in a git worktree (its sandbox cwd), so it raises gates there, not in the workspace root. That's why the chat decides gates via /sessions/{sid}/gates — the workspace-scoped route would miss them. A real subtlety worth remembering when you debug "why isn't my gate showing up."

Gates vs. the new approval system — not the same thing
Gates are coarse, turn-boundary, Vivary-native (the agent chooses to stop and ask). Approvals (Phase B) are fine-grained, mid-run, harness-enforced (the policy engine intercepts a risky action before it runs). They're complementary: keep gates for "should I do this whole plan?", add approvals for "may I run this command?"

Security & sandbox — the harness boundary

"Getting the harness right" includes its containment. Four concentric guards keep a locally-bound app from being a foothold:

Bind + token
Backend binds 127.0.0.1 only. Every route except /api/health needs the per-launch token. Two layers: the custom header forces a CORS preflight (blocks cross-origin pages), and the token blocks other local processes.
WS token hygiene
The token rides the WebSocket subprotocol offer (token.<TOKEN>), never the URL — query strings leak into logs, proxies, history. Compared with secrets.compare_digest.
Worktree isolation
Each session runs in its own detached git worktree under ~/.vivary-gui/worktrees/<sid> (when the workspace is a repo root). The agent's edits + gates are isolated there; teardown removes it.
Codex sandbox modes
The new --sandbox flag adds a second ring inside the agent: read-only (default for observability) → workspace-write → danger-full-access. Pair with the policy engine, never bypass with --dangerously-bypass-….

The engine seam — how the GUI reaches Vivary

The GUI is a shell over the published Vivary CLIs, not a fork of them. The recent "decouple the bridge" refactor means it no longer needs the monorepo's packages/ dir — it runs whatever vivary-tropo / vivary-ozone / vivary-exo / create-vivary are pip-installed in the backend's venv.

# bridge/cli.py — read-only views run the engines out-of-process for robustness
def _run_json(module, args, root):
    cmd = [sys.executable, "-m", module, *args, "--root", str(root), "--json"]
    return json.loads(subprocess.run(cmd, capture_output=True, …).stdout)

graph   = lambda root: _run_json("tropo", ["graph"], root)        # GraphPanel
blast   = lambda root,n: _run_json("tropo", ["blast", n], root)     # blast radius
review  = lambda root: _run_json("ozone", ["review"], root)       # StatePanel
board   = lambda root: _run_json("exo",   ["board"], root)        # DashboardPanel

Subprocess (not in-process import) keeps the GUI robust to engine internals and matches the engines' verified JSON contracts. The per-call latency is fine for interactive reads. Agent runtimes (codex/claude) are spawned the same way — the GUI's whole posture is "drive trusted CLIs, normalize their output."

Build plan & the keystone unknowns

Phase A — Observability

Low risk, independent, ships the wall-of-text fix on its own.

  • Capture a real Codex --json JSONL fixture (answers keystone #2).
  • CodexRuntime → exec --json + item parser; track item.id; capture thread_id; map usage → meter.
  • Extend the AgentEvent taxonomy (reasoning, tool, file_change, plan).
  • Build ToolPill / ReasoningBox / FileChange / PlanRail + density control; privilege the answer.
  • Extend api/client.ts types + the apply() reducer.
Phase B — Approval

Depends on the keystone-#1 protocol spike.

  • Spike app-server / mcp-server / exec-server: how does the GUI receive a request mid-run and send allow/deny?
  • Policy engine (services/approval.py): risk tiers, allowlist (prefix, deny-beats-allow), protected paths, circuit-breaker, persistence.
  • ApprovalCard + a Settings panel (three-rung mode + per-risk policy + allowlist mgmt).
  • Per-command risk classifier; pattern-scoped "always" that doesn't re-prompt on variation.

The four keystone unknowns (resolve before/early)

  1. Live-approval protocol — which Codex surface carries mid-run approval? (Phase B blocker; observability doesn't depend on it.)
  2. Reasoning streaming granularity — does --json emit item.updated deltas for reasoning? (Capture a fixture.)
  3. Resume semantics — codex exec resume <id> vs. app-server thread continuation.
  4. Policy persistence location — ~/.vivary-gui/ vs per-workspace .vivary/.
The gate before any of this merges (CLAUDE.md / AGENTS.md)
Implementation needs a written, human-approved ultraplan (plan mode → ExitPlanMode) before merge — intent · blast radius · verification · out-of-scope · alignment. This atlas is the shared understanding; the ultraplan is the contract for the actual edits. We enter plan mode when we start Phase A.
