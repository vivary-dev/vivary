# Vivary content and proof roadmap

Content exists to move a builder through four steps:

`understand → try on real work → verify the result → return`

Do not publish a pile of disconnected “AI productivity” posts. Every piece should
attach to a product command, proof artifact, objection, or repeatable workflow.

## Canonical surfaces

| Surface | Job |
|---|---|
| Homepage | category, outcome, adoption path, trust |
| [White paper](WHITE-PAPER.md) | the full technical argument and constraints |
| [Homepage FAQ](https://vivary.vercel.app/#faq) | quick objections, safety, privacy, package truth |
| [Architecture](ARCHITECTURE.md) | exact layer and boundary model |
| [Product roadmap](PRODUCT-ROADMAP.md) | sequence, proof goals, stop rules |
| [Getting started](GETTING-STARTED.md) | first command and successful path |
| [Walkthrough](WALKTHROUGH.md) | reproducible end-to-end proof |
| Blog | specific arguments, tutorials, release stories, and case studies |
| `/llms.txt` | compact machine-readable product and documentation truth |

Each durable fact has one owner. Posts link to canonical docs rather than copying
version tables or long command inventories.

## P0: finish the proof spine

### 1. Token-savings benchmark

Deliverables:

- methodology page;
- raw result files;
- summary chart;
- short post explaining what changed and what did not;
- reusable social crops built from the current production site assets.

The post must name model, date, task set, repository revision, and limitations.

### 2. Brownfield adoption case study

Working title: **Point Vivary at the mess**

Show:

- the starting repo;
- `tropo map`;
- dry-run adoption;
- approved files;
- doctor-clean result;
- context-budget findings;
- friction and follow-up issues.

### 3. Five-minute adoption guide

One short page and one short video:

1. map;
2. read the proposal;
3. adopt;
4. run doctor;
5. ask one real project question.

Use the actual current UI and command output. No conceptual detour before the result.

## P1: objection-led education

Build these from recurring user objections with real commands and artifacts:

1. **Why not just use `AGENTS.md`?**
2. **Typed graph vs. a giant memory file**
3. **Human gates without neutering the agent**
4. **What Vivary does not send anywhere**
5. **Why semantic memory is optional**
6. **Plain files are a feature, not a fallback**
7. **The difference between a harness and a workspace standard**
8. **Why doctor is the return loop**

Each article ends with one runnable next step, not a generic newsletter CTA.

## P2: workflow library

Every workflow article uses the same shape:

`result → starting mess → command → evidence → friction → copyable loop → gate`

Priority workflows:

- release-truth maintenance;
- large-refactor blast-radius review;
- research claim ownership;
- second-brain decision retrieval;
- long-form writing continuity;
- multi-agent claims and conflict checks;
- local/private provider setup;
- context-budget repair.

## P3: comparison and choice pages

Comparison pages are useful only when they help someone choose honestly.

Candidates:

- Vivary vs. a flat agent-memory file;
- Vivary with Claude Code vs. with Codex;
- graph-first retrieval vs. semantic recall;
- scaffold a new workspace vs. adopt an existing one;
- file storage vs. embedded storage;
- when not to use Vivary.

State evaluation criteria first. Do not write competitor takedowns or SEO pages that
pretend unlike products are interchangeable.

## Release content

Every release gets:

1. a changelog entry with exact package truth;
2. one “what this means” post;
3. one runnable command or proof image;
4. per-channel copy derived from the same canonical fact;
5. no public post until registry and live-site verification pass.

Social drafts and platform-specific assets remain in ignored private release storage,
not this public repository.

## Publishing filter

Before shipping, answer:

- Which product loop does this strengthen?
- What canonical fact does it link to?
- What can the reader run or inspect?
- Which claim is measured, which is inferred, and which remains a thesis?
- Is any version or command likely to go stale?
- Does the asset match the current production site?

If the piece has no product action, proof, or durable argument, do not publish it yet.
